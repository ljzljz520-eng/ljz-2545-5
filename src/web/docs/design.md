# 海岛灯塔导览站 · 站内设计文档

> 版本 1.0 · 更新 2026-09-30
> 本文档随站点发布，可从任意页面导航进入。所有数据为**可替换示例数据**，
> **不保证现实交通可用**。

## 1. 目标与范围

围绕一座需要乘渡轮 + 潮间堤道步行到达的海岛灯塔，提供：

- **故事页**：交通班次、观景点、潮位与适用范围、开放资料；
- **行程界面**：按时段把班次/步行/游览组合成「访问段」，支持
  **一次生成静态行程** 与 **数据变更后局部重算** 两种形态；
- **后台**：从可替换示例数据源接收船班与封闭记录，做来源版本化、矛盾检测；
- **持久化（PostgreSQL）**：保存不可变来源版本、业务数据、行程、访问段、
  段证据链，以及「数据变更 → 行程段」的**影响关系**；
- **离线包**：带冻结日期与更新缺口的历史快照，明确不保证现实交通可用。

## 2. 关键概念

| 概念 | 含义 |
|---|---|
| 来源版本 `source_versions` | 每次摄入生成一条**不可变**记录（原始 JSON + 内容指纹 + 取代指针） |
| 访问段 segment | 行程槽位：`access`（船/巴士/步行）、`visit`（游览）、`buffer` |
| 静态 static | 一次生成时按当时数据版本水位计算并冻结，**永不改变** |
| 当前 current | 数据变更后局部重算得到的最新状态 |
| 证据 evidence | 段采用/拒绝某建议所依赖的条件（班次、封闭、潮汐、坐标、接驳、锁定），可追溯到来源版本 |
| 影响关系 impact | 新版本数据对行程/段产生的影响（取消、封闭、潮汐窗口丢失、坐标变化、矛盾等） |
| 锁定 locked | 用户手动锁定的段，数据变更**不自动改写**，只给接驳连带说明 |

## 3. 数据模型（摘要，完整见 `db/schema.sql`）

```
source_versions (不可变)
  ├─< places / tide_stations / tide_points / tide_thresholds
  ├─< schedules(id, source_version_id 复合唯一)
  ├─< closures / open_materials
  └─< impact_relations >── itineraries ──< itinerary_segments ──< segment_evidence
```

- 班次按 `(业务班次 id, 来源版本 id)` 版本化，同一逻辑班次（如 F101）可在
  多个来源/版本中各有一条，规划时取生效日下的最新序列并做矛盾判定。
- `itineraries.static_snapshot` 保存一次生成结果与当时各类数据的
  **版本水位 `version_high_water`**；回滚即从该快照重建。

## 4. 硬性领域规则

1. **潮汐坐标/时区/适用范围必须匹配地点**
   - 地点声明的潮位站必须存在；
   - 潮位站 `tz` 必须与地点一致；
   - 地点必须在潮位站 `applies_to` 适用范围内；
   - 坐标距离必须 ≤ 站点声明的匹配半径（示例 800 m）。
   任一不满足，该地点的潮汐结论一律 **unknown → 不推断可通行**，
   摄入阶段还会产生 `rejected` 记录与 `station_scope_mismatch` 影响。
2. **缺测不外推**：需求步行时段必须完整落在潮位点覆盖范围之内。
   范围内相邻整点之间允许**线性插值**得到端点水位；
   覆盖不足/缺测/超范围 ⇒ `tide_unknown`，**绝不推断可通行**。
3. **临时封闭仅影响对应访问段**：只有地点匹配且时间重叠的步行/游览段
   进入 `pending_adjustment`；固定时刻的船班不因此变不可行；
   下游段只收到**接驳连带说明**（时间链可能顺延/断锚）。
4. **跨源矛盾保守处理**：
   - 最新来源声明「取消」⇒ 权威取消（旧排班不构成矛盾，只是被取代）；
   - 多个来源对同一班次给出互斥的「在航时刻」且无取消声明 ⇒ `source_conflict`，
     保守**不予采用**，给出全部变体证据。
5. **接驳约束**：相邻段间隔不得小于声明的最小缓冲（如船→巴士 10 分钟）。
   自带固定时刻的班次即使在上游断链下仍可独立到达，但会提示接驳风险。
6. **跨日**：所有时间内部以 UTC 存储，本地挂钟时间用显式 IANA 时区
   （`Asia/Shanghai`，+08:00）换算；23:30 + 50 分钟正确落到次日 00:20。

## 5. 静态生成 vs 数据变更后局部重算

### 5.1 一次生成（`staticPlan`）
1. 记录当时 ferry/closure/tide/place/material 的版本水位；
2. 按模板槽位顺序求值：班次时刻 / 步行潮汐+封闭 / 接驳间隔；
3. 结果整体写入 `static_snapshot` 与 `static_*` 列，证据写 `scope='static'`；
4. 此后该视图**只读**。

### 5.2 局部重算（`recompute`）
1. 扫描水位之后的新版本，解析出受影响槽位集合（如 F101→s1、北堤封闭→s3/s5）；
2. **仅**重算受影响槽位，其余保留（UI 标记「保留」）；
3. 时间锚定段（步行/游览）在上游断链时**级联重算**，暴露 `no_anchor`；
4. 用户锁定段保留 `locked`，不改时刻，只写接驳连带说明；
5. 为不可行段生成**替代候选**（同 OD 其他班次 / 其他低潮窗口）；
6. 写 `scope='current'` 证据、`impact_relations`，并推进版本水位（幂等）。

> 对比结论：静态回答「在我出发前看到的世界里，这趟行程成立吗」；
> 局部重算回答「世界变了之后，**只**动该动的段，每一处变化由哪个数据版本引起」。

## 6. 不可行原因 / 替代候选 / 接驳连带

结构化原因码：`cancelled`、`source_conflict`、`closed`、`tide_too_high`、
`tide_unknown`、`tide_station_mismatch`、`connection_tight`、`no_anchor`。

- **替代候选**：班次段给同 OD 在航班次（F101 取消 → F102/F900）；
  步行段给其它低潮窗口；每个候选附「采用后需逐段复核下游接驳」提示。
- **接驳连带说明**：出现在待调整/锁定段及其下游固定时刻段，明确
  「登船截止时间需重新核对」等。

## 7. 可追溯性（每个建议都能追溯到条件）

行程页每个段可展开证据链，例如一次堤道步行包含：

- `schedule`（所乘巴士，来源版本 #v，verdict=pass）
- `connection`（与上段间隔 10≥10 分钟，pass）
- `coords_match`（潮位站坐标/时区/适用范围，pass，附距离米数）
- `tide_window`（阈值、需求窗口、端点插值水位、覆盖点数）
- `closure`（若命中封闭，fail 并附封闭来源版本与时段）
- `lock`（用户锁定，warn）

每条证据都带 `source_version_id`，可一路回链到 `source_versions.raw_json`。

## 8. 离线包

`POST /api/offline-bundle` 产出：`frozen_date`、各类最新版本、
`update_gap`（生效/摄入晚于冻结日期的版本清单）、可选行程快照、免责声明。
语义：这是**历史快照**，显示「数据截止到哪天、之后还欠哪些更新」，
**不保证现实交通可用**。

## 9. 可替换数据源边界

`src/server/adapters/directory-source.js` 读取
`src/data-source/manifest.json + 各 JSON`。替换为 HTTP/GTFS/CSV 适配器时，
只要输出同一归一化 bundle（places / ferry / closures / tides / materials），
摄入、规划、页面、测试均无需改动。后台也开放
`POST /api/admin/ingest-bundle` 直接接收内存 bundle（测试与对接使用同一路径）。

## 10. 技术说明

- Node.js 内置 `http`，无 Web 框架；前端原生 ES Module。
- 持久化为真实 PostgreSQL：开发/测试使用 PGlite（WASM 内 PG），
  `db/schema.sql` 与独立 PG 完全兼容，可直接平移。
- 运行：`npm run init-db`（建表+摄入）、`npm start`、`npm test`。
